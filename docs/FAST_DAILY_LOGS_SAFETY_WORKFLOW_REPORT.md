# Fast Daily Logs — Safety & Workflow Gaps Follow-Up

Branch: `cursor/fast-daily-logs-redesign-1ab6` — **updates PR #334** (still draft, targeting `testing/full-platform-integration-2026-07`)
Status: **Draft, NOT merged, NOT deployed.** Stopped for visual owner review as requested.

The classroom-grid direction from PR #334 is approved for continued testing. This pass closes the 8 safety/workflow gaps identified before that continues.

## 1. Group Logging

New **"Log for Multiple Children"** button above the classroom grid, covering Attendance (check in/out), Meals, Bottles, Naps, Diapers/potty, Activities, and General daily update.

Flow: pick the action type → **explicitly select which children this applies to (nobody is pre-checked — "never assume every checked-in child participated")** → enter shared information once → add individual exceptions (uncheck "Included" and/or add a per-child note) → **preview** exactly who will and won't get a record → confirm. Every included child gets its own record via the same `saveDailyLogQuickAction`/`appendChildRecord` path a single-child action uses, tagged with a shared `groupLogId` for audit. Verified by test: an explicitly-excluded child and a never-selected child both get zero records; only the included children do.

## 2. Accidental Tap Recovery

Every one-tap action now shows a banner directly in the sheet: **"Logged [X] for [Child] at [time]"** with an **Undo** button. A second tap of the *same* one-tap action for the *same* child within a 4-second cooldown is silently treated as a duplicate/retry and creates no second record (`FAST_DLC_DUPLICATE_COOLDOWN_MS`).

Undo never deletes: it sets `undone: true` / `undoneAt` / `undoneBy` on the existing record (kept permanently in the store file) and that flag excludes it from every "active" view (timeline, reminders, summary) — for both the fast and classic Daily Logs UIs, via a filter added to the shared `dlcChildDaySnapshot()`.

## 3. Medication Safety

Medication is a structured form, never a single free-text field: **Child** (implicit from context), **Medication name**, **Dosage**, **Scheduled time**, **Actual time given**, **Authorization status** (explicit dropdown, no default beyond "Select…"), **Administered by**, **Notes**, **Parent notification status**.

Every value is exactly what the teacher typed — nothing is invented or defaulted by AI/heuristics. If medication name, dosage, or authorization status is left blank, the record saves with `status: "needs_provider_information"` (shown in the timeline as "⚠️ Medication — Needs Provider Information") and is **never** `shareWithFamily`. Only a fully-completed record is marked `status: "completed"`.

## 4. Summary Wording

Renamed **"AI Parent Summary"** → **"Create Parent Summary"**. The button is now **"Generate Draft"** (was "Generate Summary"), and the send button is **"Share with Parent"** (was "Send Summary") — the flow is Generate Draft → Review/Edit → Share with Parent, generated by the existing template-based `buildDailyLogParentSummary()` (no live AI/OpenAI call is made anywhere, consistent with AI Testing staying disabled).

An explicit line under the textarea states: *""Share with Parent" sends this only to the connected fake Parent/Guardian inbox for this testing account. It never sends an email, SMS, push notification, or public link.*"

## 5. Edits and Corrections

Every timeline entry now has an **Edit** button opening a correction form: **time**, **notes**, an **"Entered late"** checkbox, and a **required** reason field (saving without a reason is rejected). Saving:

- Never silently replaces the original — the first correction snapshots the original time/notes into `originalTime`/`originalNotes` (kept forever), and **every** correction (including the first) is appended to a `corrections[]` array with who/when/why.
- The entry is visibly flagged "(entered late)" in the timeline when marked so.
- A "Correction history" panel on the entry lists every past correction with its reason and timestamp.

## 6. Offline and Printing

- **Entries queue safely / never lost on refresh**: every *saved* quick action already writes straight to `localStorage` synchronously with zero network dependency — this was already true structurally and is unaffected by connectivity. What's new: an **in-progress, unsaved** note/caption now auto-saves a draft to `localStorage` on every keystroke, keyed per child+action, and is automatically restored if the tab refreshes (including while offline) before the teacher taps Save.
- **Reconnection syncs once, retries never duplicate**: the existing cloud-sync guard (`childCloudSyncing`) already prevents overlapping syncs, and the sync endpoint sends the full current snapshot each time (not incremental appends), so a retried sync can never create a duplicate record server-side.
- **Printing**: "🖨️ Print / Save PDF — Daily Report" on the Timeline (prints the full chronological timeline via the browser's print dialog) and "🖨️ Print Summary" next to Share with Parent (prints the current draft/sent parent summary) — both reuse the existing `printTextDocument()` mechanism already used elsewhere in Daily Logs.

Verified by test: filling in an incident note, going offline, refreshing the tab, coming back online, and confirming the draft is restored and saves as exactly one record (no duplicate from the refresh).

## 7. Photo Safety

- A visible warning is shown right on the Photo quick-action: *"⚠️ Testing account — use only fake/placeholder photos. Never upload a real child's photo here."*
- **Organization- and child-scoping**: when the tester is a Home Daycare Pilot sandbox account, a saved photo is now ALSO bridged (best-effort) into the server-side, organization+child-scoped Home Daycare Pilot photo store (new `addSharedPhoto`/`listSharedPhotos` in the pilot data model, new `/api/pilot/photos` routes) — closing a gap noted in the original PR #332 report ("Parent Home doesn't surface shared photos").
- **Parent sees only explicitly shared photos for their linked child**: Parent Home's `sharedPhotos` field is filtered by `sharedWithFamily !== false` and by the guardian's own access rule for that specific child — the same server-side check every other `/api/pilot/*` route already enforces.
- **No public URL**: photos are stored as `data:` URLs only; the create-photo response never even echoes the image data back.
- **Removing parent visibility never deletes the original**: `POST /api/pilot/photos/visibility` only flips `sharedWithFamily` — the provider's own photo list is unaffected either way.
- **Cross-organization access is rejected server-side**: verified by test — a second, unrelated pilot organization's tester gets zero photos back even when directly guessing another organization's `childId`.
- **Scope note**: this bridge only applies to Home Daycare Pilot sandbox testers. A plain real-account tester's Daily Logs photos remain entirely local (per-account `localStorage`, no server-side organization concept exists for that flow) — there is no "parent" to bridge to in that case, so this is an intentional no-op for her, not a gap.
